# Host 统一搜索排序设计

状态：第一版已实现。

实现参数：同词复用有效期 14 天（至少一次成功选择）；总体使用衰减周期 30 天，平滑参数 10。总体值按现有每查询次数和最后使用时间近似衰减。旧索引式脚本 ID 和文件标题哈希历史不做不可靠迁移；新选择绑定持久化 UUID 或规范化绝对路径。第三方缺少 ID 时保留 Host 内容哈希回退。SDK 和脚本插件的 Node 拼音召回使用 `pinyin-pro`，共同样本验证 Host 与插件一致。

## 目标与第一版范围

当前全局排序使用插件 `Priority + 历史加分`，但脚本为 100、文件为 `Ceiling(Lucene Score × 1000)`、应用为 `int.MaxValue`，尺度不一致。

改为插件负责召回候选，host 负责全局排序。第一版只用标题，由 host 统一进行原文、拼音和首字母匹配，不新增搜索元数据或插件权重设置。

插件也应采用兼容的规范化及匹配规则召回候选，否则结果没返回，host 就无法排序。插件可用 Lucene 等算法筛选候选，但原始分数不参与跨插件比较。召回兼容性通过共同查询样本验证。

| 搜索场景 | 排序方式 |
|---|---|
| 全局搜索 | Host 统一排序 |
| 插件内搜索 | 保留插件顺序，例如文件相关性、剪贴板时间 |
| 空输入首页 | 保留现有最近使用规则 |

## 全局排序规则

同词复用是第一优先级，包括文件搜索结果和搜索引擎操作。其余结果先按用途分组：普通候选在前，兜底操作在后。普通候选先按标题证据分段，再按来源等级、匹配层级及层内得分排序。

排序组使用 `SearchRankGroup`：`QueryReuse` → `Ordinary` → `FallbackAction`。第一版 Host 按稳定插件 ID `search-engine` 将搜索引擎结果识别为兜底操作，不增加通用插件类型或 Node 协议字段。搜索引擎标题包含当前查询只是操作描述，不代表发现了匹配候选；即使完全匹配，也排在所有普通候选之后，包括标题未命中的文件候选。有效同词复用仍可将最多一个搜索引擎操作置顶。后续别名和明确意图能力加入时，也不自动覆盖同词复用的第一优先级。

普通结果依次按标题证据分段 → 来源等级（非文件 → 文件）→ 匹配层级 → 层内得分 → 稳定 ID 排序。

标题证据使用 `SearchTitleBand`：`Exact`（完全匹配）→ `TitleMatch`（标题命中但非完全匹配）→ `Unmatched`（标题未命中）。完全匹配文件仍优先于任何非完全匹配普通结果；标题命中段内，Applications 等非文件插件的模糊匹配优先于文件的前缀匹配；所有标题命中的文件仍优先于标题未命中的非文件候选。来源等级是明确排序条件，不靠加分跨越分段。

具体匹配层级如下：

| 层级 | 匹配方式 |
|---|---|
| 1 | 标题完全匹配 |
| 2 | 标题前缀、词边界前缀匹配 |
| 3 | 标题包含、模糊、拼音或首字母匹配 |
| 4 | 插件已召回，但标题未命中 |

每个结果采用最强匹配。兜底层保留正文、路径或远程检索找到的有效候选，不因标题未命中而丢弃。

```text
层内得分 = 文本质量 × 70 + 总体使用值 × 5
```

文本质量、总体使用值为 `0～1`。文本质量考虑词边界、连续性、字符间隔、覆盖比例、多词命中及拼音转换。Host 从当前语言展示标题生成拼音和首字母，并缓存转换结果。

不要求第三方插件声明类型，也不维护所有插件的类型映射。Host 按内置文件搜索插件的稳定 ID 应用普通组每个标题证据段内的来源排后规则，按搜索引擎插件的稳定 ID 识别兜底操作组，其余插件一视同仁。这是明确排序条件，不通过分数惩罚实现；总体频率和文本质量不能突破标题证据分段、来源等级或匹配层级。

例如：有效同词复用的文件排第一；没有复用时，标题完全匹配的文件仍优先于弱匹配脚本，但在完全匹配层内排在所有非文件搜索结果之后。总体频率只提供较弱的层内调整，不跨标题证据分段、来源等级或匹配层级。参数集中在 host，通过查询样本调优。

## 历史：同词复用与总体频率分离

### 同词复用

同词指查询经过大小写、Unicode 和空白规范化后相等；不同原文、拼音、首字母输入不自动合并。

- 按 `NormalizedQuery + PluginId + ResultId` 记录成功使用。
- 最多提升一个结果：该查询最新的有效近期选择，允许跨普通匹配层级；即使来自文件搜索也排第一。
- 结果必须仍被当前查询召回并可执行；有效领域召回即使标题未命中，也可复用。
- 最新选择不可用或过期时，可回退到其他有效近期选择；其余结果正常排序。
- 用户改选后，下次跟随最新成功选择，不让旧高频选择覆盖新选择。
- 最近使用和重复选择决定复用资格，设置有效期或最低强度阈值；大量旧次数不能无限延长有效期。具体阈值实施时通过样本确定。

例如输入 `dev` 后使用“启动开发环境”，再次输入 `dev` 应优先显示它，即使新出现的 `Device Manager` 标题匹配更强。这是明确排序规则，不靠巨额加分突破层级。

### 总体使用频率

按 `PluginId + ResultId` 汇总具体结果在所有查询下的成功使用，不统计整个插件。例如同一脚本在 `dev` 下使用 10 次、`启动` 下 3 次，其总体次数为 13。

```text
每次使用贡献 = exp(-距今天数 / 衰减周期)
总体使用值 = 1 - exp(-累计贡献 / 平滑参数)
```

总体使用值有上限、随时间衰减，最多贡献 5 分，避免常用结果压过当前明显更匹配的结果。现有次数和最后使用时间可用于近似衰减，不必立即增加逐次事件表。同查询记录与全查询总体统计需分别查询，不能沿用现有前缀 boost 查询代替总体统计。

## 实现与兼容

新增三个组件：`SearchTextMatcher` 统一匹配，`SearchHistoryRanker` 处理复用资格和衰减，`GlobalResultRanker` 输出结构化排名。排名包含排序组、标题证据分段、匹配层级、是否来自内置文件搜索、层内得分及稳定键；文件搜索标记决定普通组同一标题证据段内的来源等级，复用强度用于资格判断。

| 位置 | 第一版改造 |
|---|---|
| `MyTools.Plugins/Searcher.cs` | 全局调用排序器，插件内及首页分别处理；保留 `Task.WhenAll` 后统一排序 |
| `MyTools.Common/Queries/Result.cs` | 增加保留输入顺序的构造路径，避免现有 `CreateSuccessResult` 再按 `SortScore/Priority` 重排 |
| `SearchHistoryDbHelper.cs` | 提供同查询选择记录及具体结果总体统计，替代无界 boost |
| 文件、脚本、应用插件及 SDK 匹配工具 | 验证召回兼容性，移除全局 Priority 依赖，修复脚本稳定 ID |

第一版沿用现有标题和 Node 协议。全局忽略 `Priority`，旧插件内排序暂时保留其用途。诊断记录排序组、匹配层级、文本质量、复用资格、最后选择时间及总体使用值，便于解释排名。

历史绑定稳定 ID：脚本使用配置项持久化 UUID，应用使用应用身份或规范化启动目标，文件使用规范化绝对路径。脚本不能继续用过滤后的数组索引生成 ID。旧插件保留 `ResultKey` 哈希回退；旧历史只在能可靠、唯一对应时迁移。文件重命名后身份变化是第一版限制。

Host 无法提升候选集之外的结果，文件目前前 30 项的召回限制仍需注意。候选预算协议和按历史 ID 补召回放到后续。

## 验证与后续

用脚本、应用、文件混合查询验证：

- 原文、拼音、首字母召回与 host 匹配兼容。
- 无复用时，完全匹配优先；其余标题命中结果先非文件后文件，再比较匹配层级；标题未命中结果在所有标题命中候选之后。
- Applications 模糊匹配优先于文件前缀匹配；文件完全匹配优先于应用模糊匹配；文件标题命中优先于非文件标题未命中。分段和来源排序不受文本质量或总体频率加分影响。
- 同词复用命中文件搜索时仍排第一；第三方插件无需类型声明即可参与统一排序。
- 同词最新选择可跨层优先，改选后跟随新选择，过期或失效后回退。
- 总体频率不跨层，其他结果的使用不影响当前结果，旧记录衰减且加分有上限。
- 极大 Priority、插件完成顺序不改变全局排名；同分顺序稳定。
- `vsc` 下应用的模糊匹配优先于搜索引擎生成标题的强匹配；所有普通文件候选也排在搜索引擎操作前面。
- 搜索引擎有效同词复用可置顶，失效或过期后回到兜底操作组；插件内保持插件返回顺序。
- 插件内排序、首页行为保持正确；脚本过滤及配置重排不改变身份。
- 切换语言后采用当前展示标题匹配；标题未命中的有效候选保留兜底。

.NET 验证使用独立输出目录，如 `-p:OutputPath=bin/AgentVerification/`；Node 变更执行对应 `npm run check` 和 `npm run build`。新增 UI 时遵循仓库 UI 本地化要求。

后续扩展：关键词、路径及其他名称元数据；别名和收藏；路径、URL、表达式意图识别；候选预算和历史补召回；小范围用户偏好及历史前缀复用。元数据只提供事实字段，不赋予插件全局排名权。
