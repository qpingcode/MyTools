# 插件诊断与监控需求

## 目标

提供宿主原生的 WPF 诊断窗口，用于查看所有插件的运行状态、异常和资源占用，并允许用户手动停止或重启异常插件。该功能不以插件形式实现，避免插件系统异常时诊断入口也不可用。

## 诊断窗口

诊断窗口应展示所有插件，并支持查看单个插件的详细信息：

- 插件 ID、名称、版本、是否启用
- 当前状态：未启动、启动中、运行中、重启中、已停止、异常
- 当前 `sessionId`；Node 插件同时展示进程 PID
- 断线、重启、心跳超时、请求超时和错误次数
- 消息积压与背压状态：
  - pending/in-flight 请求数及上限
  - 事件队列深度、容量和使用率
  - 最老待处理消息的等待时间
  - 累计及最近时间窗口内的丢弃事件数
  - 因达到上限返回 `TooManyRequests` 的次数
  - 队列持续高水位或满载的持续时间
- 最近一次异常及 Node stdout/stderr、退出码等诊断信息
- 最近日志，可按插件、会话、级别和时间过滤
- Node 插件的内存占用与 CPU 使用率；CPU 通过定时采样差值计算

诊断窗口提供刷新、停止插件和重启插件操作。停止和重启必须复用现有会话清理、进程树回收及重新握手流程，不能绕过 `PluginSessionManager`。

## 消息性能

Call 消息应记录从请求进入 MessageBus 到关联响应返回的耗时，覆盖 `plugin.call.*` 和 `host.call.*`。按插件、session、endpoint 和 route 汇总：

- 调用次数、成功数、失败数和超时数
- 最近一次、平均、最大响应时间
- P50、P95、P99 响应时间
- 慢调用明细，包括 `correlationId`、route、耗时和结果

不应把每次正常调用都写入高等级日志；正常调用以有界指标聚合为主，只保留慢调用和失败调用明细。

Event 是单向消息，没有响应时间，不使用 Call 的响应耗时指标。Event 应监控：

- 从进入总线到开始分发的排队时间
- 从入队到 transport 接收完成的投递时间
- 队列深度、高水位、丢弃数量和最老事件等待时间
- 按插件、session、endpoint 和 route 统计的事件吞吐量

如果 transport 的发送完成不代表插件业务已处理完成，则投递时间只能表示宿主侧交付耗时，不能表述为插件处理耗时。

## 日志

继续使用统一的应用日志文件，不为每个插件单独创建主日志文件。插件相关日志应使用以下结构化字段：

- `pluginId`
- `sessionId`
- `endpointId`（适用时）
- `route`（适用时）
- `correlationId`（适用时）
- `sequence`：进程内单调递增序号，用于同一时间戳下稳定排序
- `timestamp`

本阶段不引入 `trackId`，但日志和诊断模型应允许后续增加操作链路关联字段。

## 告警

以下情况达到阈值时，通过系统托盘通知用户：

- 连续心跳超时并判定插件失联
- 插件在短时间内反复断线或重启
- 请求持续超时或错误持续发生
- Call 的 P95/P99 或慢调用数量持续超过阈值
- 消息队列持续高水位、出现事件丢弃或频繁触发 `TooManyRequests`
- Node 进程异常退出
- 自动重启次数耗尽，插件进入停止状态

告警需要合并和限流，避免同一故障反复弹出。托盘菜单提供“插件诊断”入口，用户可随时手动打开诊断窗口。

## 数据范围

- 所有插件都应出现在诊断窗口中。
- 会话、心跳、进程和资源数据仅适用于 Node 插件。
- 计数器至少保留到本次应用退出；最近事件和日志使用有界内存缓存。
- UI 关闭后监控仍继续运行。

## 验收标准

1. 用户可从托盘菜单打开独立 WPF 诊断窗口并看到所有插件。
2. Node 插件断线、超时、重启和进程退出后，状态及计数能及时更新。
3. 异常达到阈值时出现一次受限流保护的托盘通知。
4. 用户可停止或重启 Node 插件，旧进程树和会话被正确清理。
5. 日志可按 `pluginId`、`sessionId` 和级别过滤，并按 `timestamp + sequence` 稳定排序。
6. Node 插件可展示 PID、内存和采样计算的 CPU 使用率。
7. 消息积压严重时，诊断窗口能定位到对应插件、session、endpoint 和 route，并展示队列使用率、丢弃数、拒绝数及最长等待时间。
8. Call 可展示响应时间分布及慢调用；Event 可展示排队和宿主侧投递耗时，但不标记为响应时间。
