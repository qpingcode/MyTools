# MyTools 重构与插件平台 Roadmap

## 文档目标

本文档将 MyTools 后续工作拆分为两个主项目：

1. 代码优化、整理与可读性提升
2. 插件平台建设，支持独立开发、自动加载、TypeScript 和多平台执行

每项任务都包含目标、实施方案、预期产出和完成标准，便于按阶段推进。

## 总体原则

1. 先收紧边界，再扩展能力。先让宿主、核心契约、插件实现分层清晰，再推进动态插件和跨平台。
2. 先定义协议，再做迁移。插件体系要先有稳定协议和清晰能力边界，再迁移现有插件。
3. 先解决高耦合点，再做局部可读性优化。否则后续改动会持续反复。
4. 所有重构都尽量配套最小测试保护，避免在功能仍在演进时引入回归。

## 执行 Instruction

1. 后续实现默认采用 `MVP First` 策略，优先交付最小可用链路，不先做大而全设计落地。
2. 每个阶段只实现能支撑下一阶段继续推进的最小能力集合。
3. 任何新设计都必须保留扩展点，但扩展点只体现在接口、目录结构和协议字段预留上，不在 MVP 阶段提前实现完整能力。
4. 当详细设计与 MVP 速度冲突时，优先选择更小的实现面，但不得破坏后续扩展方向。
5. 当前插件方向的 MVP 目标是：
   - 宿主能扫描插件目录
   - 宿主能读取 `plugin.json`
   - 宿主能打开插件自己的 HTML 界面
   - 宿主能把顶部搜索框内容发送给插件页面
   - 插件能自行处理搜索内容并在自己的界面中展示
6. 在 MVP 完成前，以下内容默认不做：
   - 完整权限系统
   - 完整设置系统
   - .NET 外部运行时
   - 插件市场
   - 多平台宿主实现
7. 即使 MVP 只先落地 HTML 页面插件，也必须预留后续扩展点：
   - `plugin.json` 中保留运行时字段
   - 宿主和插件之间保留统一消息桥接模型
   - 插件页面与后续 Node/.NET 后端运行时之间允许继续扩展为双向通信

## 阶段划分

### P0: 设计冻结阶段

完成目标：明确模块边界、插件协议、迁移路线，不直接大规模改代码。

### P1: 结构收敛阶段

完成目标：让现有宿主代码和插件代码可维护，降低继续迭代成本。

### P2: 插件平台落地阶段

完成目标：支持目录扫描、插件包加载、Node.js 运行时、TypeScript 插件开发。

### P3: 跨平台演进阶段

完成目标：把平台能力沉淀到宿主适配层，为 macOS 宿主预留落点。

## 项目一：代码优化、整理与可读性提升

### A1. 梳理模块边界与项目职责

目标：明确 `Common`、`Desktop`、`Plugins` 各自应该承担什么职责，停止抽象层和实现层互相渗透。

实施方案：

1. 先输出一张当前依赖图，标注哪些类型属于核心契约，哪些类型属于桌面宿主，哪些类型属于插件实现。
2. 定义目标边界：
   - 核心层只放跨平台、可序列化、与 UI 无关的契约和模型。
   - 宿主层只放窗口、热键、托盘、系统能力、插件运行时管理。
   - 插件层只放插件实现，不直接持有桌面 UI 或宿主内部对象。
3. 整理以下现存边界问题并形成迁移清单：
   - `Common` 中命名空间和职责不一致的问题。
   - `Common` 接口直接依赖插件实现模型的问题。
   - 配置系统接口和实现分散在不同层的问题。

预期产出：

1. 一份模块职责说明文档。
2. 一份类型迁移清单，说明哪些类后续要移动或重命名。

完成标准：

1. 团队可以一句话解释每个项目的职责。
2. 后续新增功能知道应落在哪一层。

### A2. 收缩全局 Service Locator 和静态入口

目标：让依赖显式化，提高可读性、可测试性和替换能力。

实施方案：

1. 先列出所有 `ServiceLocator` 使用点，按风险分为三类：
   - 启动编排类
   - ViewModel/UI 辅助类
   - 扩展方法或静态工具类
2. 优先替换启动链路中的调用，将 `AppBootstrapper`、`App.xaml.cs` 需要的依赖改为构造注入或协调服务注入。
3. 为 `WindowHelper`、`ResultItemExtensions` 这类带副作用的静态入口补一层接口，例如：
   - `ISearchWindowService`
   - `IActionExecutionService`
   - `ITrayMenuService`
4. 最后处理 ViewModel 中隐藏依赖，避免构造函数无参却依赖全局容器。

预期产出：

1. 一份依赖替换清单。
2. 一组新的宿主协调接口。

完成标准：

1. 新增功能不再需要直接调用 `ServiceLocator`。
2. 关键类的依赖关系能从构造函数直接看出来。

### A3. 拆分启动编排和宿主职责

目标：减少“上帝类”，把启动逻辑拆成容易理解和维护的几个步骤。

实施方案：

1. 将 `AppBootstrapper` 按职责拆分成独立服务：
   - 容器初始化
   - 宿主消息窗口初始化
   - 输入能力初始化（热键、手势）
   - 配置初始化
   - 插件初始化
2. 将 `App.xaml.cs` 中的托盘、语言、自动启动、设置窗口逻辑拆到专门服务，保留应用生命周期入口。
3. 为启动流程定义顺序化接口，例如 `IStartupTask`，便于以后新增步骤而不继续膨胀入口类。

预期产出：

1. 一份启动阶段说明。
2. 若干单一职责的宿主服务。

完成标准：

1. 启动链路能用 5 到 7 个步骤描述清楚。
2. 启动类只负责编排，不再直接承载细节实现。

### A4. 重构配置系统

目标：让配置系统真正成为通用能力，而不是桌面层反向控制核心层。

实施方案：

1. 重新定义配置系统边界：
   - 配置抽象和数据模型进入核心层。
   - 宿主只提供配置存储实现。
   - UI 层只负责展示和编辑。
2. 把序列化器从桌面项目中抽离，避免配置系统直接依赖宿主 UI 项目。
3. 将配置查询结果从 `object` 集合改成显式模型，减少条件分支和类型判断。
4. 把插件配置声明改为 schema 或 descriptor，而不是在插件中直接操纵 UI 结构。

预期产出：

1. 更清晰的配置模型。
2. 与插件协议兼容的设置描述结构。

完成标准：

1. 插件和宿主都能使用同一套配置契约。
2. 配置系统后续可复用到其他宿主，不依赖 WPF。

### A5. 收敛 ViewModel 复杂度

目标：让 UI 层代码更容易读、更容易测，避免一个 ViewModel 承担过多业务逻辑。

实施方案：

1. 对 `SearchViewModel` 做职责拆分：
   - 输入防抖与关键字识别
   - 视图切换与布局选择
   - 搜索状态展示
   - 动作执行路由
2. 对 `ConfigurationViewModel` 做职责拆分：
   - 分类树过滤
   - 设置搜索
   - 选择状态维护
   - 保存命令触发
3. 让 ViewModel 只保留状态和命令，复杂逻辑迁移到服务或 query object。

预期产出：

1. 更小、更直观的 ViewModel。
2. 一组可独立单测的 UI 逻辑服务。

完成标准：

1. 单个核心 ViewModel 的职责可以在一段话内说清。
2. 搜索与配置逻辑能脱离 WPF 控件独立测试。

### A6. 统一命名、清理死代码和重复注册

目标：降低阅读噪音，让代码更专业、统一。

实施方案：

1. 建立命名清理清单，重点处理：
   - 拼写错误
   - 大小写不一致
   - 带实现泄漏的命名
2. 清理明显未使用方法、重复注册和历史遗留注释代码。
3. 统一局部变量、方法参数和公共接口命名风格。
4. 对于复杂块，只补充少量高价值注释，不堆积解释性废话。

预期产出：

1. 一轮命名和清理 PR。
2. 更干净的代码基线。

完成标准：

1. 代码审查时不再反复出现拼写、重复注册、死代码等低级问题。
2. 新成员第一次阅读核心代码时不会被无关噪音打断。

### A7. 建立重构保护测试

目标：为后续拆分和迁移提供最小安全网。

实施方案：

1. 先补模块协作层面的测试，而不是只补工具函数测试。
2. 优先覆盖以下链路：
   - 插件搜索聚合
   - 关键字匹配与路由
   - 配置加载与保存
   - 结果动作执行后的副作用
3. 为高风险重构点引入 fake host service 或 test double，降低 UI 依赖。
4. 将注释掉的测试整理为明确状态：要么补齐，要么删除。

预期产出：

1. 一组针对核心协作流程的测试。
2. 更明确的测试层次划分。

完成标准：

1. 关键重构前后可以快速回归验证。
2. 不是只有字符串工具这类低价值测试在兜底。

## 项目二：插件平台建设与后续迭代能力

### B1. 定义插件平台目标架构

目标：从“编译期内置插件”演进为“宿主 + 协议 + 运行时 + SDK”。

实施方案：

1. 定义目标模块：
   - Plugin Protocol
   - Host Core
   - Host Platform Adapter
   - Plugin Runtime Node
   - Plugin Runtime DotNet
   - SDK for TypeScript
   - SDK for .NET
2. 明确插件和宿主之间只通过协议通信，不共享宿主内部对象和 UI 类型。
3. 明确插件平台的第一原则：默认进程外执行，避免类型耦合和平台绑定。

预期产出：

1. 一张目标架构图。
2. 一份术语表，统一“宿主、运行时、协议、插件包、能力”等概念。

完成标准：

1. 团队对后续插件体系的形态没有分歧。
2. 每个后续开发任务都能挂到目标模块中。

### B2. 设计插件协议和传输模型

目标：定义一套可跨语言、跨进程、跨平台的稳定插件契约。

实施方案：

1. 设计基础协议对象：
   - `PluginManifest`
   - `PluginDescriptor`
   - `SearchRequest`
   - `SearchResponse`
   - `ResultItemDto`
   - `ActionDescriptor`
   - `SettingsSchema`
   - `CapabilityRequest`
2. 所有协议对象必须满足：
   - 不依赖 WPF 类型
   - 不依赖宿主内部服务
   - 可序列化
3. 设计生命周期接口：
   - initialize
   - search
   - executeAction
   - getSettingsSchema
   - shutdown
4. 为协议增加版本字段和兼容策略，避免以后升级打断已有插件。

预期产出：

1. 一份协议草案。
2. 一份版本兼容策略说明。

完成标准：

1. TypeScript 和 .NET 两侧都能根据同一协议开发 SDK。
2. 协议不再包含宿主 UI 和平台特定类型。

### B3. 设计插件包格式和目录加载机制

目标：支持开发者独立打包插件并投放到插件目录自动加载。

实施方案：

1. 设计插件包目录结构，例如：
   - `plugin.json`
   - `dist/` 或 `bin/`
   - `assets/`
2. 在 `plugin.json` 中定义必要字段：
   - id
   - name
   - version
   - runtime
   - entry
   - supportedPlatforms
   - permissions
   - keywords
   - capabilities
3. 宿主实现插件目录扫描、manifest 校验、重复插件检测、版本检查、禁用插件跳过等逻辑。
4. 对异常插件建立隔离策略，避免一个坏插件影响宿主启动。

预期产出：

1. 插件包格式规范。
2. 动态扫描与加载流程说明。

完成标准：

1. 插件开发者不需要改宿主代码即可安装新插件。
2. 插件只要放入指定目录就能被识别和加载。

### B4. 实现 Node.js 运行时与 TypeScript SDK

目标：让 TypeScript 成为优先支持的插件开发语言。

实施方案：

1. 采用 Node.js 子进程作为 TypeScript 插件运行时。
2. 宿主与插件使用标准输入输出或本地 IPC 做消息通信。
3. 提供一个 npm SDK，封装协议细节，让开发者只实现简洁接口。
4. 提供一个最小 demo 插件模板，验证从开发、构建、打包到加载的完整链路。
5. 提供本地开发调试能力，例如开发模式下直接从源码目录加载。

预期产出：

1. `mytools-plugin-sdk-ts`。
2. 一个可运行的示例 TypeScript 插件。
3. 一套插件开发模板脚手架。

完成标准：

1. 可以用 TypeScript 独立开发一个插件并被宿主加载。
2. 开发者不需要引用主项目源码。

### B5. 实现 .NET 外部运行时和兼容策略

目标：保留现有 .NET 技术栈优势，同时逐步摆脱进程内耦合。

实施方案：

1. 设计 .NET 插件外部运行时，使其与 TypeScript 插件共享同一套协议。
2. 为现有 C# 插件提供迁移适配层，避免一次性重写。
3. 将原有 `PluginBase` 风格逐步替换为 SDK 风格，不再依赖宿主内部 DI。
4. 允许一定时期内同时支持：
   - 旧版内置插件
   - 新版外部 .NET 插件
   - 新版 TypeScript 插件

预期产出：

1. `MyTools.PluginSdk.DotNet`。
2. 旧插件迁移指南。

完成标准：

1. C# 插件可以独立打包、独立运行。
2. 宿主可在过渡期兼容旧插件和新插件。

### B6. 抽象宿主能力，建立权限模型

目标：把平台能力从插件实现中剥离出来，使插件能跨平台运行。

实施方案：

1. 列出现有插件依赖的宿主能力：
   - 剪贴板
   - 打开文件或目录
   - 打开 URL
   - 本地存储
   - 网络访问
   - 通知
   - 日志
2. 定义统一 capability API，由宿主按平台实现。
3. 在 manifest 中声明权限，宿主根据权限暴露能力。
4. 对明显平台绑定的功能单独分类，不混入通用插件协议。

预期产出：

1. 一份 Host Capabilities 清单。
2. 一份插件权限模型。

完成标准：

1. 通用插件不直接调用 Windows API。
2. 将来迁移到 macOS 时只需补宿主适配层。

### B7. 重构现有插件分类与迁移顺序

目标：把现有插件按迁移难度和平台依赖程度分类，避免全量硬迁移。

实施方案：

1. 将现有插件分为三类：
   - 可优先迁移为跨平台插件
   - 需要宿主能力适配后迁移
   - 明确属于平台特化功能，先留在宿主侧
2. 优先迁移以下候选：
   - Calculator
   - JsonFormatter
   - XmlFormatter
   - SearchEngine
   - Translator
3. 暂缓或改造以下平台强绑定能力：
   - ClipBoard
   - ProcessKiller
   - OpenInExplorer 类动作
   - 默认浏览器探测
   - 任何依赖注册表、WPF、Explorer 或系统消息的能力
4. 为每个插件建立迁移卡片，记录依赖、风险、是否需要 capability。

预期产出：

1. 一份插件迁移矩阵。
2. 一套插件迁移优先级。

完成标准：

1. 能明确知道每个现有插件下一步怎么处理。
2. 插件迁移不会和宿主重构互相打架。

### B8. 建立开发者体验和发布流程

目标：让插件开发成为低门槛、可复制的工程流程。

实施方案：

1. 为 TypeScript 和 .NET 各提供一个插件模板。
2. 提供插件开发文档：
   - 如何创建插件
   - 如何本地调试
   - 如何打包
   - 如何声明权限
   - 如何定义设置
3. 提供宿主侧插件诊断页或日志入口，便于排查加载失败、权限不足、协议错误等问题。
4. 设计插件版本兼容和升级策略。

预期产出：

1. 插件开发者文档。
2. 示例插件模板。
3. 最小可用发布流程。

完成标准：

1. 新插件开发可以按模板独立完成。
2. 插件加载失败时有清晰定位信息。

## 两个项目之间的依赖关系

1. A1、A2、A4 是 B1、B2 的前置条件。
2. A3 和 A5 能降低宿主后续接入新插件运行时的复杂度。
3. A7 是 B3 到 B7 的保护网，没有测试就不适合大规模迁移。
4. B6 会反过来推动 A1 的模块边界收敛。

## 里程碑建议

### M1: 宿主边界清晰

标志：能够清楚区分核心契约、宿主实现、插件实现，关键入口不再依赖全局定位器。

### M2: 协议与插件包成型

标志：已有稳定协议草案、manifest 结构和插件目录扫描机制。

### M3: 第一个 TypeScript 插件跑通

标志：平台能力已被宿主适配层隔离，插件协议不再依赖 Windows 特定对象。

## 风险与注意事项

1. 不要在协议未稳定前大规模迁移现有插件，否则会重复返工。
2. 不要试图把所有现有平台能力都塞进“通用插件”概念中，宿主能力必须独立建模。
3. 不要继续新增基于 `ServiceLocator` 和静态 helper 的能力，否则会抵消重构收益。
4. 不要把 WPF 类型、图像对象、宿主服务直接放进未来插件 SDK。
5. 如果需要兼容期，必须明确旧插件模型和新插件模型的生命周期边界。
