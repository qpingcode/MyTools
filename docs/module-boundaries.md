# MyTools 模块边界说明

## 目的

本文档用于落实 Roadmap 中的 A1，明确当前项目的职责边界、现存问题和目标分层，为后续重构与插件平台演进提供统一依据。

## 当前项目结构

当前核心项目如下：

1. `MyTools.Common`
2. `MyTools.Plugins`
3. `MyTools.Desktop`

当前引用关系：

1. `MyTools.Plugins` 依赖 `MyTools.Common`
2. `MyTools.Desktop` 依赖 `MyTools.Common`
3. `MyTools.Desktop` 依赖 `MyTools.Plugins`

## 当前状态总结

### 现有职责分布

#### MyTools.Common

当前主要承载内容：

1. 一部分基础接口和公共模型
2. 一部分插件契约和查询模型
3. 一部分依赖注入辅助能力
4. 一部分配置抽象

当前问题：

1. 项目名叫 `Common`，但内部既有通用契约，也有插件语义、配置语义、运行期工具。
2. 部分类型在 `Common` 项目中，却属于 `MyTools.Plugins` 命名空间，语义不一致。
3. 一些“抽象层”接口直接依赖插件对象，导致 `Common` 不是纯核心层。

#### MyTools.Plugins

当前主要承载内容：

1. 各个内置插件实现
2. 插件注册与搜索聚合
3. 动作执行模型的一部分实现
4. 插件帮助类和 Windows 相关能力

当前问题：

1. 项目本身是 `net8.0-windows` 且启用 WPF，不是可移植的插件层。
2. 项目中既有“可移植业务插件”，也有“Windows 宿主集成能力”，两者混在一起。
3. 插件加载方式仍然是编译期注册，不具备独立开发、投放目录自动加载的边界。

#### MyTools.Desktop

当前主要承载内容：

1. WPF 宿主和窗口层
2. 启动编排、热键、手势、托盘等宿主能力
3. 配置系统实现
4. UI 辅助逻辑和 ViewModel

当前问题：

1. 宿主入口承担了过多编排和细节实现。
2. 一些本应属于核心能力的实现放在了桌面层，例如配置系统实现。
3. 宿主层通过静态入口和 `ServiceLocator` 向外泄漏内部依赖。

## 已确认的边界问题

### 问题 1：核心层与插件层语义交叉

典型表现：

1. `MyTools.Common/Plugins/IPlugin.cs` 位于 Common 项目中，但命名空间是 `MyTools.Plugins`。
2. `IKeywordRegistry`、`IGlobalSearchRegistry`、`IHotKeyRegistry` 这类 Common 接口直接引用 `IPlugin`。

影响：

1. 代码阅读时无法快速判断哪些类型是核心契约，哪些类型是插件实现。
2. 后续插件 SDK 无法直接复用当前契约。
3. 未来若要做进程外插件或跨语言插件，现有边界会造成强耦合。

### 问题 2：配置系统边界反转

典型表现：

1. `IConfigurationRegistry` 位于 Common。
2. `ConfigurationRegistry` 实现位于 Desktop。
3. `ConfigurationRegistry` 直接依赖 `MyTools.Desktop.Serializers`。

影响：

1. 插件与核心逻辑实际被桌面宿主实现牵制。
2. 配置能力无法自然复用到未来宿主。
3. 配置系统难以成为插件协议的一部分。

### 问题 3：宿主能力与插件能力混杂

典型表现：

1. `MyTools.Plugins` 中存在直接依赖 WPF、剪贴板、注册表、Windows Shell 的代码。
2. 某些“插件”实际是平台集成功能，而不是可移植业务扩展。

影响：

1. 插件层无法跨平台。
2. 宿主能力无法清晰建模为 capability。
3. 后续 TypeScript 插件无法对齐当前插件模型。

### 问题 4：插件注册与发现边界不成立

典型表现：

1. 插件通过 `AddSingleton<IPlugin, XxxPlugin>()` 编译期注册。
2. 关键字和能力通过 `PluginLoader` 中的具体类型判断绑定。

影响：

1. 新插件必须修改主项目代码，无法独立开发。
2. 插件生命周期和宿主容器深度耦合。
3. 无法自然演进到目录扫描和插件包模式。

## 目标分层

后续建议将系统收敛为四层结构。

### 第一层：核心契约层

建议命名：`MyTools.Core` 或 `MyTools.Abstractions`

职责：

1. 纯契约和纯模型
2. 与 UI 无关、与平台无关、可序列化的对象
3. 插件协议共享模型
4. 配置抽象、查询模型、动作描述模型

约束：

1. 不依赖 WPF
2. 不依赖 Windows API
3. 不依赖宿主内部容器
4. 不出现桌面层或具体插件实现类型

### 第二层：宿主核心层

建议命名：`MyTools.Host.Core`

职责：

1. 启动编排
2. 插件发现、校验、生命周期管理
3. 搜索聚合、结果路由、权限与能力协调
4. 配置注册、插件设置接入、日志和诊断

约束：

1. 不直接依赖具体桌面 UI
2. 不直接依赖某个插件实现类
3. 默认以协议和 manifest 驱动插件接入

### 第三层：宿主平台适配层

建议命名：

1. `MyTools.Host.Windows`
2. `MyTools.Host.Mac`（未来）

职责：

1. 窗口、托盘、热键、手势、系统消息
2. 剪贴板、文件打开、通知、Shell 集成
3. 平台相关 capability 的落地实现

约束：

1. 明确承认平台相关性
2. 不把平台 API 直接暴露给插件

### 第四层：插件实现层

建议拆分为：

1. 内置插件实现
2. 外部 .NET 插件
3. TypeScript 插件

职责：

1. 按插件协议提供搜索、动作、预览、设置描述
2. 不直接依赖宿主内部类
3. 通过 host capability 访问受控系统能力

约束：

1. 不直接依赖 WPF 类型
2. 不依赖 `ServiceLocator`
3. 不要求和宿主同进程

## 模块职责定义

### 核心契约层应该包含什么

1. 插件协议 DTO
2. 结果模型和动作描述模型
3. 配置抽象接口和 schema 模型
4. 搜索请求、响应、预览模型
5. 与宿主和插件共享的错误模型、版本模型

### 核心契约层不应该包含什么

1. `ServiceLocator`
2. WPF 图像、窗口、控件相关类型
3. 平台热键、系统消息、剪贴板实现
4. 具体插件类或宿主实现类

### 宿主核心层应该包含什么

1. 插件目录扫描
2. manifest 校验
3. 插件运行时调度
4. 搜索聚合和结果整形
5. capability 调度与权限检查

### 宿主平台层应该包含什么

1. `App` 和桌面生命周期适配
2. 热键管理、托盘、手势等平台服务
3. 平台特有 shell 和系统能力实现

### 插件实现层应该包含什么

1. 每个插件的业务逻辑
2. 插件自己的默认配置描述
3. 插件运行时入口

## 判断新增代码应该落在哪一层

可使用以下规则：

1. 如果类型需要被 TypeScript SDK 和 .NET SDK 共同理解，应放核心契约层。
2. 如果类型依赖窗口、热键、托盘、剪贴板或系统消息，应放宿主平台层。
3. 如果类型负责插件扫描、运行时调度、聚合结果，应放宿主核心层。
4. 如果类型是某个插件的业务规则或搜索逻辑，应放插件实现层。
5. 如果某个类型必须引用具体插件类名才能工作，说明当前边界设计仍需继续收敛。

## 本阶段结论

当前 MyTools 的主要结构问题不是项目数量不够，而是职责边界没有形成稳定分层。A1 的结论如下：

1. `Common` 应演进为真正的核心契约层。
2. `Desktop` 应收敛为宿主与平台适配层，而不是承载通用实现。
3. `Plugins` 应从“Windows 内置插件集合”演进为“插件实现层”，并逐步脱离宿主内部依赖。
4. 配置系统、插件契约和宿主能力需要重新收边界，否则后续插件平台建设会持续返工。
